### Wire size — one point on a curve

The single-entry wire-size numbers below are for the exact fixture
this run used: an 18-character filename (`entry_%08zu.log`) inside a
`char[256]` buffer. That point matters because it is what the fixture
generates, not because it is representative of a random workload.

| Encoding    | This fixture (B) | Scales with `name` length? | Formula                        |
|-------------|------------------|----------------------------|--------------------------------|
| **Iris**    | **292**          | No — fixed                 | 12 header + 280 struct         |
| Protobuf    | 32               | Yes — linear               | ≈ 12 int-fields + 2 + `L`      |
| FlatBuffers | 72               | Yes — linear + vtable      | ≈ 20 fixed + `L` + padding     |

The Iris 292 B breaks down as: 12 B frame header (8 B TypeId + 4 B
size, LE) + 8 B `size` + 8 B `mtime` + 4 B `mode` + 4 B `type` + 256 B
`name` buffer. Every field is at a compile-time offset, so the
receiver decodes with one `memcpy`; the trade-off is that the 256 B
buffer is on the wire whether the filename is 3 chars or 200.

Protobuf's 32 B is not compression — it is variable-length encoding:
varints for the integers (1–5 B each), a length prefix + raw bytes for
the string (no NUL padding), and default-valued fields (`type == 0`)
omitted entirely. Nothing is compressed; nothing is padded.

**Where the ratio actually lies** for the same struct, computed from
the formulas above:

| `name` length (chars) | Iris (B) | Protobuf (B) | Iris / Protobuf |
|-----------------------|----------|--------------|-----------------|
| 0 (name omitted)      | 292      | 12           | 24.3×           |
| 18 (this fixture)     | 292      | 32           | 9.1×            |
| 64                    | 292      | 78           | 3.74×           |
| 128                   | 292      | 143          | 2.04×           |
| 200                   | 292      | 215          | 1.36×           |
| 255 (buffer limit)    | 292      | 270          | 1.08×           |

The ratio narrows sharply as `name` fills the buffer, and the buffer
size is itself a schema knob — a `char[64]` `DirEntry` would be 100 B
on the wire regardless of filename, versus roughly `14 + L` for
Protobuf. Iris is never smaller than Protobuf at the same logical
value (there's a ~22-byte header/tag delta on top of any unused
buffer tail), but the two get arbitrarily close as the buffer fills.
**What we're measuring is the padding overhead of a generously-sized
fixed buffer, not a general "Iris is 9× larger than Protobuf" claim.**
The right question for a given system is: how much of the fixed
buffer is actually used, and does saving the decode work matter more
than saving the tail bytes.

**The trade-off is deliberate.** Encode is one `memcpy` because the
sender does not scan or measure anything — the layout is the schema.
Decode is one `memcpy` because the receiver does not tag-parse. See
[docs/design/dod-and-games.md](../design/dod-and-games.md) for why the
constraint matters in game-loop and authentication contexts.

Decode-batch is where Iris's fixed layout shines: **~83 M entries/s**
in a single-thread walk, ~8.7× Protobuf and ~2.5× FlatBuffers.

## Iris-specific micro-benchmarks (median, ns)

| Case                                | Value    | Notes                                                     |
|-------------------------------------|----------|-----------------------------------------------------------|
| `type_id_of<DirEntry>()` lookup     | **0.13** | Single load — inlined and constant-folded per TU          |
| `iris::wrap(DirEntry)`              | 18.9     | Allocates an `IrisBuffer`, memcpys 280 B in               |

TypeId lookup at ~0.1 ns is essentially free — this is why we can
afford to include the TypeId on every wire frame without runtime cost.

## Interpretation

Three lines describe the shape:

1. **Iris is fastest on every case measured** — because "encode" is a
   `memcpy` of a known-size struct, and "decode" is the same in
   reverse. Neither Protobuf nor FlatBuffers can be this simple on a
   variable-layout format.
2. **Iris pays for it on the wire when the buffer is loosely filled.**
   At this fixture's 18-char filename inside a `char[256]`, Iris is
   9× larger than Protobuf; at a 200-char filename it is 1.35× larger
   (see the size-scaling table above). If the link is the bottleneck
   and the buffer is mostly empty, Protobuf still wins wall-clock —
   pick the CStr size for your workload, or use a variable-length
   `Bytes` field if you have wildly variable strings.
3. **On a Unix pipe or loopback socket** (~5–20 GB/s), the CPU cost of
   encode/decode dominates and Iris wins by the ratios above.

Neither of these is news to anyone who has read the design docs —
this run just confirms the theoretical shape empirically. When we
have a reference box we'll re-run and fill in
[`RESULTS_TEMPLATE.md`](RESULTS_TEMPLATE.md).

## Known limits of this run

- **Power policy**: EPP=`balance_performance`. Numbers will be
  modestly (~1.1×–1.3×) faster with EPP=`performance` or on a
  desktop-class chip with a fixed high clock.
- **SMT**: enabled. Neighbour hyperthreads can spike variance.
- **Turbo**: enabled but was not boosting during the run (base 3.30
  GHz P-core observed).
- **Only DirEntry, only one `name` length**: 280 B fixed struct with a
  `char[256]` filled to 18 chars. Wire-size ratios shift substantially
  with `name` length and with the buffer size we chose (see the
  scaling table); adding fixture variants (short-name, near-full-name,
  no-CStr `Bytes`-field) is on the follow-up list. Different fixture
  shapes (many small ints, one big blob, sparse-optional fields) will
  shift the story further: FlatBuffers advantages grow for
  many-optional-field cases; Protobuf advantages grow for
  small-magnitude integer fields (varints).
- **Not measured**: setup cost of Protobuf arenas, FlatBuffers builder
  reuse, actual socket / pipe transfer, contention.
