## Single-entry cases (median wall time, ns)

| Case              | Iris | Protobuf | FlatBuffers | Iris speedup vs PB / FB |
|-------------------|------|----------|-------------|-------------------------|
| Encode            | 19.2 | 83.5     | 54.0        | **4.3× / 2.8×**         |
| Decode            | 9.8  | 105.5    | 34.7        | **10.7× / 3.5×**        |
| Roundtrip         | 30.1 | 190.2    | 85.9        | **6.3× / 2.9×**         |
| **Wire size (B)** | **292** | **32** | **72**     | (Iris 9× / 4× *larger*) |

The Iris wire is **fixed**: 12-byte header + `sizeof(DirEntry)` =
292 bytes for every entry, regardless of `name` length. Protobuf
uses varints and length-prefixed strings; FlatBuffers uses vtables +
padded strings.

**The tradeoff is deliberate.** Encode is one `memcpy` because the
sender does not scan or measure anything — the layout is the schema.
Decode is one `memcpy` because the receiver does not tag-parse. See
[docs/design/dod-and-games.md](../design/dod-and-games.md) for why the
constraint matters in game-loop and authentication contexts.

## Batch cases (N = 10 000)

| Case         | Iris (µs / M items/s) | Protobuf (µs / M items/s) | FlatBuffers (µs / M items/s) |
|--------------|-----------------------|---------------------------|------------------------------|
| Encode 10K   | 414 / 24.2            | 977 / 10.4                | 668 / 15.2                   |
| Decode 10K   | 122 / 82.9            | 1061 / 9.6                | 303 / 33.2                   |

Decode-batch is where Iris's fixed layout shines: **~83 M entries/s**
in a single-thread walk, ~8.7× Protobuf and ~2.5× FlatBuffers.

## Iris-specific micro-benchmarks (median, ns)

| Case                                | Value    | Notes                                                     |
|-------------------------------------|----------|-----------------------------------------------------------|
| `type_id_of<DirEntry>()` lookup     | **0.13** | Single load — inlined and constant-folded per TU          |
| `iris::wrap(DirEntry)`              | 18.9     | Allocates an `IrisBuffer`, memcpys 280 B in               |
| `iris::unwrap<DirEntry>(v)`         | 3.2      | memcpy 280 B out                                          |
| `wrap → unwrap` roundtrip           | 22.0     | ~= wrap + unwrap; no extra bookkeeping                    |
| Wrap batch 10K                      | 457 µs   | ~22 M wraps/s; dominated by 10 K heap allocations         |

TypeId lookup at ~0.1 ns is essentially free — this is why we can
afford to include the TypeId on every wire frame without runtime cost.

## Interpretation

Three lines describe the shape:

1. **Iris is fastest on every case measured** — because "encode" is a
   `memcpy` of a known-size struct, and "decode" is the same in
   reverse. Neither Protobuf nor FlatBuffers can be this simple on a
   variable-layout format.
2. **Iris pays for it on the wire**: 292 B vs 32 B (Protobuf). If your
   bottleneck is a 1 GbE link with a small hot field, Protobuf still
   wins on wall-clock end-to-end because you send 9× less.
3. **On a Unix pipe or loopback socket** (~5–20 GB/s), the CPU cost of
   encode/decode dominates and Iris wins by the ratios above.

Neither of these is news to anyone who has read the design docs —
this run just confirms the theoretical shape empirically. When we
have a reference box we'll re-run and fill in
[`RESULTS_TEMPLATE.md`](RESULTS_TEMPLATE.md).

## Known limits of this run

- **Governor**: `powersave`. Numbers will be ~1.2×–1.5× faster on a
  `performance`-governed workstation.
- **SMT**: enabled. Neighbour hyperthreads can spike variance.
- **Turbo**: enabled but was not boosting during the run (base 3.30
  GHz P-core observed).
- **Only DirEntry**: 280 B fixed struct with one `char[256]`. Different
  fixture shapes (many small ints, one big blob, sparse-optional fields)
  will shift the story. FlatBuffers advantages grow for many-optional-field
  cases; Protobuf advantages grow for compressible integer fields.
- **Not measured**: setup cost of Protobuf arenas, FlatBuffers builder
  reuse, actual socket / pipe transfer, contention.
